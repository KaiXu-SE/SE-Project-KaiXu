# KaiXu（开序）软件开发过程模型选型

## 选型结论

根据[选型 Issue #9 的组内讨论](https://github.com/KaiXu-SE/SE-Project-KaiXu/issues/9)，KaiXu 采用**增量模型组织交付，在每个增量内按短迭代推进**。增量确定每一版给学生交付的可用功能及验收场景。短迭代用于安排版内的计划、构造、测试和评审。

[调研报告](../requirements/research-report.md)显示，学生即使只使用本地桌面端，也需要把课程作业排进实际可用的时间。先验证本地任务、固定事件和个人工作时段的关系，再引入账号、同步和共享权限，能让四人团队按版本集中联调。Canvas 授权和课表数据格式需要尽早验证，测试结果用于调整外部接入的安排。[项目章程](project-charter.md)和[仓库里程碑](https://github.com/KaiXu-SE/SE-Project-KaiXu/milestones)记录了三版的交付范围与计划发布日期。

## 候选方案与取舍

| 方案 | 在 KaiXu 中的适用性 | 取舍 |
| --- | --- | --- |
| 增量模型 | 个人排期可以独立使用，小组协作依赖任务与时段规则，外部接入可以接在稳定的录入流程后。三版都能形成可演示、可验收的版本。 | 用作主交付模型。每版固定验收场景，后续版本回归前一版的关键功能。 |
| 螺旋模型 | 按风险组织每一轮，适合反复验证 Canvas 授权、断网重连和多人编辑冲突。 | 将风险分析和小样本验证放进迭代计划。按三个业务增量安排日常交付，便于团队集中联调和准备课程检查。 |
| 统一过程（UP） | 迭代式推进，强调用例、架构和风险，适合组织课程要求的需求规格、分析模型与设计评审。 | 采用用例追踪和设计评审做法。按课程检查点安排文档和评审，将它们纳入各版计划。 |
| 敏捷开发 | 短周期反馈适合打磨排期规则和交互细节，也便于四人团队根据试用和测试调整优先级。 | 版内采用短迭代和回顾。每轮通过 Issue 记录范围和验收条件，已确认的基线按变更流程更新。 |

## 交付版本与验收场景

| 增量与计划发布日期 | 本版交付 | 代表性验收场景 |
| --- | --- | --- |
| **M1 · v0.1.0 · 2026-12-11** 个人工作区与时间规划 | Windows 本地课程和项目工作区、任务、固定事件、分段排期、日／周视图、链接与文本资料。归档 SRS、分析模型和设计评审记录。 | 在未登录的桌面端建一门课，手动创建一项独立任务和一项课程任务。把课程任务排到两天，确认与课程重叠或超出截止日期时有提示。重启后核对任务字段、状态和时段，验证工作区可归档和恢复。 |
| **M2 · v0.2.0 · 2026-12-16** 账号同步与小组协作 | 账号与服务端、桌面离线补传、成员邀请与所有权交接、共享任务和共同事件。Android 在线查看日程、更新任务状态和调整本人已有时段。 | 用访客及 A、B 两个账号验证隔离。A 在桌面断网修改并重启，重连重试只生效一次，两个账号同时改同一任务时能核对差异。B 被移出项目后，用原会话访问共享任务或事件应被拒绝，仍能查阅自己的工作时段。用 Android 实测在线状态更新和改期。 |
| **M3 · v0.3.0 · 2026-12-24** 外部接入与全量验收 | Canvas 作业只读拉取、标准课表导入、任务资料关联与附件版本、规则排程、Android 在线番茄钟。课程群消息和 AI 提取按选定扩展项安排。 | 两种外部来源均先预览再确认、重复导入不产生重复记录。验证旧附件可恢复、排程草案经确认才写入、番茄钟断网暂停并在重连后核对时长。回归 M1 和 M2，按章程口径完成性能测试并留存部署和发布记录。 |

章程将 Android 快速录入列入产品范围。该功能的交付版本及链接、笔记等资料的共享排期，由需求负责人和章程负责人核对后记入对应里程碑，补齐验收标准。

## 迭代计划、评审与回顾

以下为 M1 的两轮拟定安排。M2 和 M3 沿用同一流程，按各自里程碑拆分任务。

| 轮次 | 计划与构造 | 测试与评审 |
| --- | --- | --- |
| **第 1 轮，基础排期**。拟于 12 月 8 日前完成本地流程演练。 | 用 `US-02` 和 `US-06` 确定手动建任务与分段排期的验收条件。在 Windows 本地端实现任务、截止日期、工作时段与日／周视图的基本流程。 | 未登录时建一项有截止日期的作业并排到两个时段，核对原截止日期与两个时段分别保存、视图一致。评审时演示，从测试结果中整理下一轮待处理问题。 |
| **第 2 轮，冲突提示与重启恢复**。拟于 12 月 10 日前完成复测。 | 用 `US-07` 确定重叠、相邻和超期的行为。在第一轮基础上接入跨工作区的冲突检查，核对重启后的任务状态和时段数据。 | 复测重叠会提示、相邻时段可保存、超期会提示。退出并重启后核对既有记录，回归第一轮建任务和排期。评审后记录遗留问题和是否达到 M1 签收条件。 |

每轮开始时在 Issue 或看板记录目标、关联需求、负责人、验收场景和计划日期。构造时用关联 PR 保留修改记录。测试记录引用[需求追溯任务 #11](https://github.com/KaiXu-SE/SE-Project-KaiXu/issues/11)的用例编号，并记下测试版本、实际结果、缺陷及待回归事项。PR 须经至少一名非作者组员批准，且必需的自动检查通过后方可合并。两轮之间至少轮换一次结对或评审对象。结束时在 `docs/iterations/` 归档迭代计划与回顾，并关联实际 PR 和测试证据。回顾写明完成项、未完成项及下一轮调整。

## 外部接入的提前验证

| 验证项 | 时间与验证方法 | 结果和对交付的影响 |
| --- | --- | --- |
| Canvas 授权和真实作业拉取 | 按里程碑在 2026-11-27 前，用获授权账号从一门真实课程发起只读试拉取。核对作业标识、标题、截止日期（如有）和原作业链接。 | **待验证。** 在关联 Issue 记录脱敏样本、实际结果和阻塞原因。若授权或字段不满足预期，保留手动录入能力，由团队确定补验时间并更新 M3 风险。 |
| 学期课表文件 | M1 期间尽早选取脱敏样本，验证课程名称、星期、节次和周次能否解析，核对预览、确认后创建课程与固定事件的规则。 | **待验证。** 记录样本格式、预期和实际结果。遇到格式差异时，明确支持的模板和失败提示，并把受影响的验收场景纳入 M3 计划。 |

每次验证记录日期、参与人、证据链接、实际结论和对交付日期或范围的影响。需要调整已确认的范围时，按[协作与提交规范](../../CONTRIBUTING.md)提交 `type:change` Issue，经组内评审后更新里程碑、相关需求和验收记录。
